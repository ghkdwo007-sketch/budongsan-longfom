# 부동산롱폼 — 편집 프로파일

비블 부동산 롱폼(대표님 & 미빅님 Q&A 등) 전용 워크플로. 2캠 교차편집 + 컷편집 + 자막.
회차마다 이 문서 순서대로 돌리면 된다. 새로 알게 된 건 여기와 `glossary.txt` 에 계속 쌓는다.

**최초 확립: 2026-07-29** — 2캠 Q&A 회차로 전 과정을 돌려보며 정리했다.

> 폴더명은 `budongsan-longfom` 인데 명령은 `--profile 부동산롱폼` 이다. 오타가 아니라
> `config.json` 의 `"_프로파일"` 별칭으로 찾는다. 한글 폴더명은 맥(NFD)과 윈도우(NFC)가
> 다르게 저장해서 외장 SSD 를 오가면 중복 커밋된다 — 그래서 폴더만 ASCII 로 뒀다.

## 한 줄로 돌리기

```bash
python engine/run_episode.py \
  --cam1 "D:/.../cam01/DJI_xxxx.MP4" \
  --cam2 "D:/.../cam02/DJI_yyyy.MP4" \
  --profile 부동산롱폼
```

0~6단계(TC0 사본 → 싱크 → 컷 → 자막 → 오디오 → EDL → 검증)를 순서대로 실행한다.
`--offset` 을 주면 싱크 측정을 건너뛰고, `--skip-remux` 로 TC0 사본 생성을 건너뛴다.

`--segments output/<base>_segments.json` 을 주면 **7단계(카테고리 분류 + 축약본)**까지 만든다.
구간 판단은 전사본을 읽어야 하는 일이라 자동화하지 않았다 — Claude Code 에
"카테고리 나누고 N분 하이라이트 만들어줘" 라고 하면 JSON 을 만들고 실행까지 해준다.

납품 전 검증만 따로:
```bash
python engine/verify_episode.py "<cam01 원본.MP4>" --cam2
```

아래는 각 단계에서 **왜 그렇게 하는지** — 순서를 바꾸거나 생략하면 깨지는 이유들이다.

## 작업 환경

| | |
|---|---|
| OS | Windows 11 · Python 3.11 · ffmpeg 8.1.2 |
| GPU | RTX 4060 8GB (faster-whisper CUDA) |
| 편집 | **Adobe Premiere Pro 26.3.0** |
| 소스 | DJI 카메라 2대, 4K HEVC 3840×2160 @ 29.97fps, 약 30분 / 11GB |

## [핵심] Premiere 26 은 FCP7 XML 을 못 읽는다

26.3 설치 폴더에 xmeml 임포터가 **없다**(AAF·OMF·EDL 만 남음). 가져오기 형식 목록에도 없다.
작은 XML(5~10컷)은 우연히 통과하지만 20컷만 넘어도 "프로젝트가 손상되어 열 수 없습니다"로 실패한다.

→ **핸드오프는 EDL 로 한다.** `_cut.xml` / `_mcam.xml` 은 Premiere 25 이하·타 NLE 용으로만 남겨둔다.

## 순서

### 0) 소스 준비 — TC0 사본 (필수)

EDL 은 파일 경로가 아니라 **릴 이름 + 타임코드**로 미디어를 찾는다. 그래서
**파일의 TC 와 EDL 의 TC 기준이 반드시 같아야 한다.** DJI 파일은 카메라 시계가 박혀 있고
(예: cam01 `23:50:03;28`, cam02 `20:21:28;04`) 두 캠이 서로 다르다.

두 캠 **모두** TC 0 사본을 만든다. 재인코딩 없음(컨테이너만 다시 씀) → 화질 손실 0, 1~3분.

```bash
ffmpeg -i cam01/원본.MP4 -map 0:v:0 -map 0:a:0 -c copy -timecode 00:00:00:00 cam01/cam01_TC0.MP4
ffmpeg -i cam02/원본.MP4 -map 0:v:0 -map 0:a:0 -c copy -timecode 00:00:00:00 cam02/cam02_TC0.MP4
```

`-map 0:v:0 -map 0:a:0` 는 DJI 가 붙이는 mjpeg 썸네일·데이터 스트림을 떼어낸다(파일도 가벼워짐).

> **실패 사례**: cam02 만 실제 TC(20:21…)로 EDL 을 만들었더니, 프리미어가 미디어 TC 를 0 으로 잡아
> 20시간대 지점을 맞추려고 **23시간짜리 유령 클립**을 만들었다. 컷 위치·길이가 전부 어긋나고 렉도 심해진다.
> 프리미어의 `클립 수정 > 시간 코드` 는 **오프라인 클립에서 비활성**이라 이걸로는 해결이 안 된다.

### 1) 싱크 오프셋

```bash
python engine/sync_2cam.py "cam01/cam01_TC0.MP4" "cam02/cam02_TC0.MP4"
```

파일명 타임스탬프는 믿지 말 것 (실측에서 28초 차이로 표시됐지만 실제는 1.04초였다).
`engine/` 밖에서 구간별 재측정으로 드리프트도 확인하면 좋다 — 실측 30분 누적 18.8ms(0.56프레임)로 보정 불필요.

### 2) 컷편집

```bash
python engine/auto_cut.py "cam01/cam01_TC0.MP4" --preset 표준 --profile 부동산롱폼
```

- 프리셋은 **표준**. `공격`은 추임새를 지워 이 채널의 말맛(만담·반복 개그)을 죽인다.
- `--profile` 이 자막 25자 등 이 코너 설정을 얹는다.

#### [중요] 컷은 오디오가 거의 0인 자리에서만 낸다 (2026-07-30)

비블 피드백: **말이 채 끝나기 전에 끊겨서 다음 컷과의 연결이 부자연스러웠다.**
원인이 두 군데였고, 설정과 코드 양쪽을 고쳤다.

**① 무음 컷 경계** — 프로파일 값으로 해결.

| | 전 | 후 | 이유 |
|---|---|---|---|
| `NOISE_DB` | -45 | **-50** | 더 조용해야 무음으로 인정 = "거의 0" |
| `PAD_LEAD` | 0.15 | **0.30** | 말 끝난 뒤 여유를 두 배로 (어미 울림 보존) |
| `PAD_TAIL` | 0.10 | **0.12** | |
| `MIN_SILENCE` | 0.45 | **0.70** | 패딩을 키운 만큼 함께 올려야 한다 ↓ |
| `MIN_REMOVE` | (없음) | **0.20** | |

> **`PAD_LEAD+PAD_TAIL` 과 `MIN_SILENCE` 는 같이 움직여야 한다.** 패딩 합이 무음 길이에
> 가까워지면 '지우는 건 50ms인데 접합부는 생기는' 미세컷이 대량으로 생긴다. 새 값은
> 0.42 vs 0.70 이라 컷당 최소 0.28초를 지운다. `MIN_REMOVE` 는 이 여유가 그보다도
> 작아지는 자리를 아예 컷하지 않게 하는 안전망이다(패딩만 키우면 무음 흡수로 자동
> 병합되지만, 경계값 부근을 확실히 막는다).

**② 말 도중을 잘라내는 제거** — 설정으로 표현이 안 돼 `engine/cut_gate.py` 를 새로 만들었다.

더듬/중복·NG·망설임·숨소리는 전사본의 단어 타임스탬프로 구간을 잡는데, whisper 의 단어
경계는 ±100~200ms 흔들린다. **전사상 '단어 사이 빈틈'인 자리가 실제로는 아직 말이 울리는
중**이라 거기서 이어붙으면 음절이 잘린다. `WORD_SNAP` 은 경계가 단어 구간을 '엄격히 관통'할
때만 고치므로 이걸 못 잡는다 — 타임스탬프 자체가 틀린 것이기 때문이다.

가드는 이어붙을 두 지점의 실제 RMS 를 재서 ① 조용하면 통과 ② 아니면 근처에서 조용한 자리를
찾아 옮기고 ③ 그래도 없으면 **그 제거를 포기한다**(반복 구간에서 소리가 겹쳐 끊을 자리가
없으면 놔두는 게 낫다는 편집 방향). 기준은 `노이즈플로어 + CUT_GATE_MARGIN(6dB)` 로,
회차마다 녹음 레벨이 달라도 따라간다. 포기한 구간은 리포트의 `가드보류` 항목에 남는다.

> **가드는 두 번 돌아야 한다.** 제거 목록만 검사하면 부족하다 — 그 뒤 `WORD_SNAP` 이
> 경계를 단어 끝으로 되돌리고, 무음 컷 경계는 애초에 첫 패스를 거치지 않는다.
> 그래서 최종 컷 목록에 한 번 더 패스를 돌린다(`gate_keeps`). 여기서 '포기'는
> **두 컷을 합쳐 그 자리를 안 끊는 것**이다.
>
> **판정은 프레임 격자에서 해야 한다.** 자막 드리프트 때와 같은 함정이다. 실수 초로
> '조용하다'고 판정해도 XML/EDL 은 프레임으로 반올림하므로 최대 반 프레임(29.97p = 17ms)
> 밀려 발화 시작에 걸린다. 양자화를 맞추기 전엔 마지막 패스가 13곳만 잡았는데,
> 맞춘 뒤 58곳을 잡았다.

**실측 (260729 Q&A 3편, 같은 전사 캐시로 비교)** — 접합부 음량을 정리 오디오에서 직접 측정:

| | 변경 전 | 변경 후 |
|---|---|---|
| 컷 | 285개 | **207개** |
| 러닝타임 | 26:14 | **27:50** (+1:36) |
| 접합부 음량 중앙값 | -31.4dB | **-35.9dB** |
| p90 | -12.1dB | **-33.4dB** |
| 최대(가장 시끄러운 접합부) | **-4.1dB** | **-32.5dB** |
| 기준(-33dB) 초과 | 311/568 (54.8%) | **3/412 (0.7%)** |

원본의 12.8% 를 지우던 것이 7.5% 로 줄었다 — **의도한 트레이드오프다.** 제1원칙이
'자연스러움 > 최대 제거' 이고, 말 한복판에서 끊던 접합부(최대 -4.1dB = 또렷한 발화)가
전부 사라졌다. 더 타이트하게 가고 싶으면 `CUT_GATE_MARGIN` 을 올린다(느슨해짐).

> **`output/<base>_words.json` 을 절대 지우지 말 것.** 전사 캐시다.
> 지우면 재전사가 일어나는데 faster-whisper(GPU float16)는 비결정적이라 결과가 달라지고,
> 그 차이가 말더듬·숨소리 판정으로 증폭돼 **컷 개수가 크게 바뀐다** (실측 210컷/26:45 ↔ 285컷/26:14).

### 3) 자막 — 반드시 이 순서

```bash
python engine/apply_glossary.py "output/<base>_cut.srt" --profile 부동산롱폼   # ① 교정
python engine/subtitle_polish.py "output/<base>_cut.srt"                      # ② 25자 분할
```

**순서를 바꾸면 안 된다.** 분할 후에 교정하면 줄 나눔이 달라져 문맥 규칙이 안 맞는다.
분할본을 되돌리려다 `.srt.bak` 을 잘못 복원해 교정을 통째로 날린 적이 있다 —
교정 완료본은 `output/_keep/` 에 따로 복사해 두는 게 안전하다.

- 한 줄 **25자**, 2줄 금지 (비블 자막 = 한 줄 + 검은 박스. 25자가 화면 폭의 약 2/3)
- **온점(.)·쉼표(,)는 넣지 않는다.** `? !` 와 `... …`(말 끄는 표현), 숫자 안의 점·쉼표(`1.2%`, `8,500`)는 남긴다.
  `SUB_STRIP_PUNCT` 가 처리하며, 앞 단계들이 문장부호로 줄 경계를 판단하므로 **맨 마지막에** 적용된다.

### [중요] 자막 싱크 — 두 곳에서 어긋났었다

1. **비례 분할 금지.** 25자 제한은 `regroup(max_chars=)` 로 **처음부터** 지킨다.
   이미 만든 자막을 `subtitle_polish` 가 쪼개면 시간을 글자수 비례로 나눠 실제 발화와 어긋난다(실측 최대 850ms).
   분할이 0건이어야 정상 — 로그의 `633→633` 처럼 개수가 안 늘어야 한다.
2. **타임라인 양자화.** `build_mapper(keeps, fps=...)` 로 영상 XML과 **같은 프레임 단위**로 누적해야 한다.
   실수로 누적하면 클립마다 ±1프레임씩 어긋나 285컷에 걸쳐 쌓인다 (실측 평균 204ms · 최대 349ms, 뒤로 갈수록 심함).

### 4) 오디오

```bash
python engine/make_cut_audio.py "cam01/cam01_TC0.MP4"
```

`_cut_audio_flat.wav` (컷 적용된 단일 파일)를 A1 의 `00:00:00:00` 에 올린다.

> **오디오를 EDL 이벤트로 쪼개지 말 것.** 한 이벤트에 릴 2개(비디오+오디오)를 쓰면
> 프리미어가 오디오 소스 in점을 무시하고 **매 컷마다 0부터 재생**한다.
> 그리고 플랫 오디오는 **샘플 단위로 잘라야** 한다 — ffmpeg concat 디먹서의 inpoint/outpoint 는
> 구간마다 밀려서 285구간에 12.6초나 초과했다. 지금 구현은 오차 0.1ms.

### 5) EDL

```bash
python engine/make_edl.py "cam01/cam01_TC0.MP4" --cam2 "cam02/cam02_TC0.MP4" <오프셋초>
```

> **EDL 타임코드는 30프레임까지다.** 59.94p 이상 소스를 60프레임 TC(`00:00:20:58`)로 쓰면
> 프리미어가 프레임 필드 30 이상을 못 읽고 클립을 엉뚱한 자리에 놓는다 — 증상은
> **타임라인 중간중간 빈 공백 + 오디오 싱크 어긋남**. 엔진이 30fps 초과 소스는
> **소스 2프레임 = TC 1프레임**으로 접어 29.97 DF 로 쓴다(컷 지점은 33ms 격자에 스냅).
> 이 코너는 29.97p 라 그대로지만, 카메라를 60p 로 바꾸면 바로 걸리는 부분이다.
>
> **fps 를 상수로 박지 말 것.** `make_edl`·`make_cut_audio`·`verify_episode` 에 29.97 이
> 상수로 있었다. `_cut.xml` 의 프레임 번호는 **소스 실제 fps 단위**라, 59.94p 회차에서
> 컷이 2배로 어긋나고 오디오가 절반 길이로 잘렸다. 지금은 `probe_media` 로 받아 쓴다.
>
> **`* FROM CLIP NAME` 은 모든 이벤트가 같아야 한다.** 프리미어는 이 값으로 미디어 항목을
> 구분한다. 값이 다르면 이벤트 수만큼 별개 오프라인 클립이 생겨 **미디어 연결을 클립 수만큼
> 손으로** 해야 한다(실측 93클립 = 93번). 이름은 실제 연결할 파일명(`_TC0.MP4`)과 같게 둔다 —
> 그래야 '미디어 연결'에서 프리미어가 자동으로 찾는다.
>
> **멀티캠은 컷을 절대 빼지 말 것.** 범위를 벗어나는 컷(그 캠이 아직/이미 녹화 전후)은
> 제외하지 말고 소스만 clamp 한다. 컷 개수·레코드 TC 가 캠마다 같아야
> 레이어를 겹쳐 교차편집(클립 활성/비활성)을 할 수 있다.
> 제외했더니 208 vs 285 가 되면서 시퀀스 시작 TC까지 어긋났다.

### 6) 프리미어 조립

1. 각 `.edl` 가져오기 → 오프라인 릴에 **미디어 연결**
   - `CAM01` → `cam01_TC0.MP4` / `CAM02` → `cam02_TC0.MP4`
2. cam02 시퀀스 전체 복사 → cam01 시퀀스 **V2** 에 `00:00:00:00` 기준 붙여넣기
3. `_cut_audio_flat.wav` → **A1** 의 `00:00:00:00`
4. `_cut.srt` 가져오기
5. 타임라인 전체 선택 → **Ctrl+Shift+D** (컷 클릭음 제거)

교차편집은 V2 클립을 구간별로 활성/비활성해서 쓴다.

### 7) 카테고리 분류 + 축약본 (선택)

긴 회차를 짧게 줄이거나 내용을 카테고리로 나눠 보고 싶을 때.

```bash
python engine/make_highlight.py "<원본.MP4>" --segments output/<base>_segments.json
```

구간 JSON 은 **컷 타임라인(=`_cut.srt` 와 같은 기준)** 의 `M:SS` 로 쓴다.
`keep:false` 인 구간은 축약본에서 빠진다(제작 지시·잡담·중복).

산출물: `_final.edl`(축약본) · `_highlight_audio.wav` · `_highlight.srt` ·
`_full_labeled.edl`(전체) · `_categories.md`(구간 근거 + 조립 순서).

> **카테고리를 트랙으로 나누지 말 것.** 카테고리마다 EDL 을 뽑아 V2·V3… 에 쌓아 봤는데
> 못 쓴다 — 카테고리 경계가 컷 중간을 갈라 104컷이 129조각이 되고, 각 EDL 이 자기 구간만
> 갖고 나머지는 비어 있어 조립이 안 된다. **시퀀스 하나**에 담고 컷은 쪼개지 않는다.
> (카테고리를 클립 이름에 넣는 것도 안 된다 — 위 `FROM CLIP NAME` 항목 참고)
>
> **오디오·자막은 EDL 이 선언한 클립 길이에서 만든다.** 구간 단위로 따로 자르면 스냅·반올림이
> 어긋나 A/V 싱크가 밀린다(실측 5.0ms → 0.1ms). 자막은 클립 경계에서 토막나므로
> (469줄 중 80줄이 76ms 조각) 같은 문장을 다시 병합한다.

### 시퀀스 설정 · 들어갔는지 확인

시퀀스는 **소스와 같은 프레임레이트**로 만든다. 타임베이스는 **생성 후에 못 바꾸므로**
틀렸으면 시퀀스를 지우고 다시 만들어야 한다.

가져온 직후 **마지막 클립이 끝나는 타임코드**가 `make_edl`/`make_highlight` 가 찍어준
시퀀스 길이와 같은지 본다. **2배로 나오면 타임베이스가 절반으로 잡힌 것**이다.

- 프로젝트 설정 > 렌더러 **Mercury Playback Engine GPU 가속(CUDA)**
- 1080p 시퀀스 + "프레임 크기로 조정"
- 그래도 무거우면 **프록시**(720p 올인트라)를 만들어 붙인다

## 이 코너의 편집 방향

- **자연스러움 > 최대 제거.** 반복이 개그다 — "빨리빨리 찍어봐", "10억 10억", "떴어 떴어",
  "본진의 1등을 잡아라" 반복은 살린다. 엔진이 '더듬/중복'으로 지우면 되살릴 것.
- 고유명사 오인식은 채널 신뢰도에 직결한다. 특히 **송도/성도**, **병점역 아이파크캐슬**,
  **신생아 특례대출** — `glossary.txt` 로 매회 잡는다.
- 실제로 말하지 않은 **브랜드명 환청**(예: BHC)은 반드시 제거한다.
- 판단이 갈리는 표현(예: 수위 있는 농담)은 임의로 고치지 말고 편집자에게 물어본다.
